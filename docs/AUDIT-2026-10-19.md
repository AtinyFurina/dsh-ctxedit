## 0. 总评

这是一份**考古型**代码：它不是在 DSH 提供的扩展点上做插件，而是逆向了宿主会话日志的 surface 语义，用「合成的合法轮次 + 非 assistant 载体遮蔽」硬造出「模型可见历史可编辑」。这类代码天生脆弱，但作者把每条硬约束都写进了注释，并留下校验器证据——这是它最值钱的部分，比代码本身值钱。

扣分点集中在三处：

1. **一个核心功能（还原原样）实际上是死的，测试却报 ✅。**
2. **文档三个文件停在三/四个不同版本。**
3. **客户端靠注入 CSS 类名与 DOM 选择器干活，带 1.5 秒全树轮询；无版本控制，一次误改没有回退路径。**

> **复核更新（2026-10-19，两轮）**：收到接手 agent 的反驳后逐条复核，**4 条反驳全部成立**（第 4 条是对方补充出处、并同时更正了它自己上一条里「system 载体必须第一个 surface 节点」的说法）。已修正四处结论：P0-2 降级为 P1 并重写方案 B（§2）、P2-4 降级为 P3（§4）、`primitives` 结论撤回（§5）、`system/developer` step 约束补上出处（§10.4）。过程与证据见 **§10**。

## 2. 严重问题

### P0-1 「还原原样」是死功能，而离线测试报 ✅

**现象**：面板里永远不会出现「还原原样」按钮；`/find` 返回的 `history.rewrites` 恒为 0。

**根因（两处断，任一处都足以致命）**

(a) 血统回溯方向错了。`shadowLineage`（grep `function shadowLineage`）从**当前可见节点自己的** `surfaceOp` 往回爬：

```js
const event = bySeq.get(current)
if (!event || !(event.surfaceOp && typeof event.surfaceOp === 'object')) break
const shadowed = event.surfaceOp.startSeq
```

但插件写出的替换载体是 `user/message`（grep `function shadowEvent`），而合成助手消息写的是 `surfaceOp: 'append'`（grep `function appendAssistantTurn`）。落盘值确认为字符串 `"append"`（宿主 `dsh-session/lib/index.js:193`：`return isSurfaceEvent(event) && event.surfaceOp === "append"`）。于是第一跳就 `break`，`rewrites` 恒为 0。

(b) 客户端按钮被这个 0 挡住：`lib/client.js` grep `history?.rewrites > 0` 才渲染「还原原样」；面板里的「已改过 N 次」同理恒不显示。

**实证 1**（4 条真实会话，含 397 个可见助手节点的长会话）：

```
synth seq 25 turn 2 surfaceOp "append" visible true rewrites 0
visible assistant nodes 397   with rewrites>0: 0
```

**实证 2**：即使绕过 UI 直接 `POST /apply mode=restore`，`originSeq` 会解析成 **它自己**，写出的「原稿」就是改写版正文（grep `mode === 'restore'` 分支）。

**实证 3**：直接运行仓库自带脚本（工作区根目录执行）：

```powershell
node tools\test-restore.mjs "$env:USERPROFILE\.dsh\sessions\--C-Users-AtinyFurina-Desktop-~65E5~5E38~5BF9~8BDD--\session-057e35b4-...\session.v4.jsonl.zstd"
```

真实输出：

```
目标 seq=80（user/message，被改过 1 次，血统 80→79）
原始版本 seq=79（user/message），正文 ""
❌ 关系状态机  !! current-generation delivery marker names the wrong Session
✅ Session.fromRestore + 模型读到的末条助手消息  → 原稿已回到视野：""
✅ 轮次号严格连续  → 1,2,3,4,5,6,7,8
✅ 可见助手消息无同 id 重复  → 5 条，全唯一
exit=0
```

同时暴露三个测试缺陷：

1. **目标选错**：`tools/test-restore.mjs:65-67` 在「所有可见节点」里找 `rewrites>0`，真实日志里的候选全是 `user/message` 载体和 `system/message`，**永远不是 restore 真正要处理的 assistant 消息**。
2. **断言空转**：原始版本正文是 `""`，断言 `txt !== origText` 变成 `"" !== ""`，于是打印「原稿已回到视野：""」。
3. **失败不退出**：`res()`（`tools/test-restore.mjs:92`）吞异常，全程无 `process.exit(1)`，❌ 之后 `exit=0`。
4. 附带：那个 ❌ 是**误伤** —— 测试重建 header 时丢了 `parentSession` / `agentPreset`，而校验器依赖 `header.parentSession`（`dsh-session-format-v3-to-v4/lib/index.js:1034`）。即测试在这类被 fork 过的会话上输入的判定前提本身就是错的。

**建议**：二选一，不要留着现在这种「UI 不给入口、API 还能调出错结果」的状态。

- 方案 A（修）：把 `shadowLineage` 改成「按 `sourceEventSeqs` 反查遮蔽我的那条载体」，即从候选 carrier 里找 `startSeq <= nodeSeq <= endSeq` 且节点仍在 surface 上的那条，再顺着 carrier 自己的 `surfaceOp.startSeq` 往上爬。
- 方案 B（删）：0.5.1 明确废弃 `restore` 模式，移除按钮与文案，并在 CHANGELOG 写明。

**验收标准**

- 构造「改写一次 → 打开新消息面板」场景，`/find` 返回 `history.rewrites === 1`、`history.originSeq` 指向原稿 seq；
- `POST /apply mode=restore` 后 `deriveMessages()` 里最后一条 assistant 的正文 === 原稿正文（非空、非改写版）；
- `tools/test-restore.mjs` 在上述场景固定失败/成功后 `process.exit(0|1)` 正确。

### P0-2 空载体确实会投影成空消息；文档里两句话互相矛盾，实测「会投影」是对的

> **严重度：P1（原判 P0，2026-10-19 复核后降级，见 §10.3）。**
> 降级理由：事实（会投影、文档自相矛盾）成立且可复现，但**不破坏功能**。原 P0 定级的第二条依据「可能被某个 provider 拒绝」是**我方未实测的推测**——§8 自己就标了未验证，却拿它支撑定级，违反了本报告的证据纪律。该推测现已从定级依据中移除。

**现象**：每次抹掉/改写/留标记，模型请求里都会多一条 `content: []` 的 user 消息。

**矛盾证据**

- `lib/index.js` grep `遮蔽一个节点` 的注释：「空内容（不会投影成消息）」
- `README.md:45`：「用无回合的 user/message 空内容载体做（空内容不会投影成消息）」
- 同文件 grep `纯撤回时用零宽空格` 的注释：「空 content 的 user/message 仍会投影成一条空消息进入模型请求（实测）」

两者只能有一个对。

**实证**：用宿主自己的 `Session.fromRestore(...).deriveMessages()` 跑真实日志：

```
messages 22  emptyLike 4  zwsp 1
EMPTY/NO-PARTS msg role= user content= []   ×3
ZWSP msg role= user text= "\u200b"
```

**为什么不能靠「换个 content」解决**（宿主源码，`dsh-session/lib/index.js:217-230`，`types/surface.js:75-106` 同构）：

```js
case "user/message": return event.data;              // 空 content 也会返回
case "system/message":
case "developer/message":
case "assistant/message":
  if (event.data.message.content.length === 0) return null;
  return event.data.message;
```

**user 载体天然投影，要真正「零投影」只能换载体类型。**

**建议**：二选一，并**删掉 README 第 45 行那句错的**。

- **方案 A（推荐，低成本）**：接受空/ZWSP 载体为已知代价，写进 README「已知限制」，把每次编辑多 1 条空 user 消息明确记为设计取舍。改动只在文档。
- **方案 B（可行但重，成本已逐条核实）**：改用 `system/message` 载体——它 `content.length === 0` 时 `deriveEventMessage` 返回 null（`dsh-session/lib/index.js:222-226`），是目前唯一能真正做到「零投影」的载体类型。代价：

  | # | 约束 | 出处 |
  |---|---|---|
  | 1 | `data.turn`、`data.step` 必须是正整数 | `v3-to-v4/lib/index.js:252-256`（`assertV4SystemMessageFields`） |
  | 2 | `message.role === "system"`、`content` 为数组 | 同处 `:259-261` |
  | 3 | `source.kind === "system-prompt"` | `dsh-session/lib/index.js:1208-1210` |
  | 4 | 因为 `system/message ∈ STEP_EVENT_TYPES`，必须落在**开着的 turn + step** 里 | `v3-to-v4:492-495`、`requireStep` `:573-575`、`accept()` `:742` |

  因此每次遮蔽都要多写一个合成轮次（约 5 条：`turn/start → step/start → system/message → step/end → turn/end`）+ 一次轮次计数器同步，并伪造 `system-prompt` 来源语义。
  **额外风险**：第 4 条约束在 `session.append` 时**不检查**（append 只做 payload 校验，`dsh-session/lib/index.js:1196-1218`），要到**下次加载/恢复**才由 `restoreReleasedV4Artifact → assertReleasedV4Relationships` 触发（`v3-to-v4:982 → :1000 → :742`；持久化侧扫描器 `dsh-session-persistence-jsonl` 的 `finish()` 同样调用）。即：**写坏可能当场无事、重开会话才炸**——这比「写入即被拒」更危险，实施时必须补恢复期回归。
  **`developer/message` 不适合**：`headerSeq` 必须指向更早的 `request/header`（`:581-584`），内容仅限 `tool-addition`（`:586-595`），且同样在 `STEP_EVENT_TYPES` 里。

**验收标准（二选一，按所选方案）**

- 方案 A：README「已知限制」明确写「每次就地编辑会向模型请求注入 1 条空 user 消息」；同文件不再出现「空内容不会投影成消息」的错误陈述。
- 方案 B：做完一次抹掉 / 一次改写 / 一次标记后，`deriveMessages()` 中不存在 `content.length === 0` 的 user 消息；关系校验器 + 轮次连续性同时通过；**并额外做一次「写完后重开会话」的恢复校验**（`restoreReleasedV4Artifact`），确认没有写坏。

## 4. P2 —— 建议修

1. **长度限制自相矛盾**：请求体封顶 256KB（grep `MAX_BODY_BYTES`），正文封顶 120,000 字符（grep `MAX_TEXT_CHARS`）。12 万汉字 JSON 化约 **360KB**，永远进不了门；且超限与「JSON 坏了」共用同一个 `400 invalid JSON body`（grep `function readJsonBody`），排障会被误导。建议：`MAX_BODY_BYTES` 提到 1MB，或按字符数换算后校验；超限返回 413。
2. **`/rewind` 先 fork 再校验**（grep `resend 需要非空正文`）：`resend` 正文为空的 400 是在**已经创建子会话、已经写了标记行之后**才返回。用户看到失败，侧栏里多了一条 fork。建议：把正文校验提到 `controller.fork` 之前。
3. **`zones.json` 非原子、无 schema、无清理**（grep `function readZones` / `function writeZones`）：直接 `writeFileSync` 覆盖，损坏后 `readZones()` 静默返回 `{}` —— 界面上被隐藏的行全部复活，而模型侧仍隐藏。实测文件里已有 6 个会话、16 条区域，只增不删。建议：临时文件 + rename、读入时校验字段类型、按会话剪枝。
4. **`/rewind-here` 的 `hiddenTurns` 可能多隐藏（复核后降级 P3，见 §10.2）**：把锚点所在整轮塞进隐藏集合。若锚点是**轮中间的 steering 消息**，同轮在锚点之前的行也会被藏掉。但「回溯」按钮只注入到 `[data-chat-flow-kind="user"]` 行，steering 是独立 kind（`dsh-client-ui-chat/lib/client.js:3810`、`:7190-7196`、`:9130`），UI 上拿不到 steering 锚点；**只有直接调 API 并传 steering 的 messageId 才可能触发**。改写为已知限制即可，不必按 P2 修。
5. **客户端 DOM 寄生式实现**（grep `function FlowRewind`）：依赖 `[data-chat-flow-key]`、`data-chat-turn`、`class*="_bubble"`、`[data-slot="conversation.chat.flow"]` 等未公开内部约定；`MutationObserver(document.body, {childList, subtree})` + 1500ms 轮询，长会话里每次流式输出都触发全树 `querySelectorAll` 重扫。平台改版时会**静默失效**（选择器不匹配就什么都不发生）。建议：至少加一个「自检」入口（检测选择器命中数为 0 时在面板里提示「本平台版本可能不兼容」）。

## 6. 安全评估：合格，但措辞别说过头

7/7 路由都调了 `isLoopbackRequest`（grep `function isLoopbackRequest`）：远端必须是 `127.0.0.1` / `::1` / `::ffff:127.0.0.1`，Host 必须是回环主机名（挡 DNS rebinding）—— **LAN 确实进不来**。

- `Origin` 缺失时**直接放行** → 浏览器场景挡得住，本机任意进程/脚本挡不住。
- 无 CSRF token、无鉴权；`/zones` 传任意 sessionId 都返回（只读）。
- `sec-fetch-site` 只拒 `cross-site`。

**判定**：README 写「只接受回环地址 + 同源请求」，准确说是「回环为真、同源为条件真」。个人单机环境可接受，但别把它当权限边界。

### 10.2 反驳二：`hiddenTurns` 多隐藏当前 UI 不可达 —— 成立，降级 P3

### 10.3 反驳三：P0-2 的验收标准按当前 surface 语义不可达 —— 成立，重写并降级

### 10.4 反驳四：`system/developer` 载体的 step 约束 —— 成立，出处已核对

第二轮我写的是「没找到『必须在开着的 step 里』的直接证据」。对方补了出处，我逐条核对，**全部成立**：
